## 2026-10-27：exe 无版本信息（FileVersion/ProductName 读不到，Win10/Win11 资源管理器空白）

### 现象
- 资源管理器「详细信息/版本」与 PowerShell `Get-Item .VersionInfo` 读不到
  FileVersion / ProductName / CompanyName（全部为空字符串），且**资源类型里 Language 全是 0000**。

### 根因
- Tauri 2 时代（tauri-winres 0.3）构建的版本资源带 `VarFileInfo/Translation`，Windows 能读；
  降级到 **Tauri 1**（tauri-build 1.x 用的 tauri-winres 0.1）生成的 VERSIONINFO
  **缺少 `VarFileInfo/Translation` 块** → Windows 无法把 StringFileInfo 的字符串表
  对应到具体语言 → 资源管理器读不出来（块其实在，等于没有）。
- 想在 build.rs 里用 tauri-winres 0.3 叠加注入也不行，本机有两个坑：
  1. **src-tauri 目录有 rustup override = `stable-x86_64-pc-windows-gnu`**（不是 MSVC）；
  2. 该工具链**没有任何资源编译器**：没有 rc.exe / llvm-rc / 真 GNU windres
     （`C:\Users\550414\.cargo\bin\windres.exe` 是个只打印报错的 shim）
     → embed-resource 3.x 编译 .rc 必然失败。

### 修复（构建后脚本，零编译器依赖）
- 新增 `scripts/qp_fix_version.py`：Python ctypes 直调 kernel32
  `BeginUpdateResourceW / UpdateResourceW / EndUpdateResourceW`，按 Win32 版本资源规范
  手工构造完整 VERSIONINFO（**含 VarFileInfo/Translation 0x0409-04B0**）注入已编译的 exe。
- 用法：`python scripts/qp_fix_version.py <exe> <版本号>`，在 `tauri build` 完成、
  `QuickCopy.exe` 重命名后执行。三端版本同步改版本号时必须同步传参更新。

### 验证
- `Get-Item exe .VersionInfo`：FileVersion=0.2.18 / ProductVersion=0.2.18 /
  ProductName=QuickCopy / CompanyName=QuickCopy / 中文 FileDescription ✅
- 安装目录部署后 MD5 与构建产物一致 ✅

### 预防
- 发布 PC 构建产物前必须跑一次 `qp_fix_version.py`，并把它写进发布清单/流程。
- 千万别再手改 Tauri 版本号同步逻辑（旧 Tauri 2 版本块与 Tauri 1 的行为差异是本次根因源头）。

## 2026-10-27：托盘菜单「关于与升级」等全部无反应

### 现象
- 托盘图标右键菜单点「关于与升级 / 打开设置」等无任何反应；左键切换主界面正常。

### 根因
- Tauri 1 的托盘菜单项点击事件走 **`SystemTrayEvent::MenuItemClick`**，
  **不是 `on_menu_event`**（后者只收窗口菜单事件；之前误把分发逻辑放那里，托盘点击收不到）。
- `on_system_tray_event` 里只处理了 `LeftClick`，没有 `MenuItemClick` 分支 → 菜单项点击被静默丢弃。

### 修复
- `lib.rs on_system_tray_event` 增加 `SystemTrayEvent::MenuItemClick { id, .. }` 分发：
  `show` → `toggle_main`；`settings` → 显示主窗 + `qp:open-settings` 事件；
  `about` → `qp_show_about`（取 tauri.conf 静态声明的 `about` 窗口 unminimize/show/center/focus）；
  `quit` → 退出。菜单项 id 与托盘配置一致（show/settings/about/quit）。

### 验证
- 静态确认：`build_tray()` 菜单 4 项存在；`on_system_tray_event` 已注册新分支；`qp_show_about`
  命令取静态声明窗口；编译通过；启动后关于窗口「关于与升级」已创建（隐藏，EnumWindows 可见）✅
- 托盘右键自动点击注入在 Win11 下被系统拦（UIA 可见图标但鼠标注入不生效），**真机人工复核**
  右键菜单各项点击。

### 预防
- Tauri 1（乃至 2）的托盘菜单事件一律放 `on_system_tray_event`；`on_menu_event` 只管窗口菜单。
- 改托盘菜单项 id 时必须同步改 `on_system_tray_event` 的分发匹配。

## 2026-10-27：窗口从圆角变直角（Tauri 2 构建 → Tauri 1 构建后 DWM 圆角丢失）

### 现象
- 用户反馈窗口 4 个角本应是圆角（之前一直圆角），某次升级后变成直角。

### 根因
- 旧安装版是 **Tauri 2 时代构建**：无边框窗口（`decorations:false`）在 Windows 11 默认自带
  系统圆角（DWM `DWMWCP_ROUND`）。
- 项目已降级到 **Tauri 1**：无边框窗口的 DWM corner preference 是 `DEFAULT`，Windows 11 对
  无边框（WS_POPUP）顶层窗口**不自动圆角** → 直角。
- 本机从旧 Tauri 2 安装版切换到 Tauri 1 构建后，用户立刻发现窗口变直角。

### 修复
- `lib.rs apply_win_round_corners()`：启动时对主窗口调用
  `DwmSetWindowAttribute(hwnd, DWMWA_WINDOW_CORNER_PREFERENCE=33, DWMWCP_ROUND=2)`，
  `#[link(name = "dwmapi")]` 直接声明，不新增 crate 依赖；Win11 22H2+ 支持（老系统忽略失败）。

### 验证
- 像素级检查四角：顶点为非窗口背景色（圆角切角透出桌面），角内 16px 为窗口背景色 `#e9edf2` ✅
- `--hidden` 静默启动仍正常（圆角设置在 setup 中，隐藏窗口同样生效）✅

### 预防
- 更改 Tauri 大版本后**必须核对窗口视觉**（圆角/阴影/无边框行为差异：Tauri 2 默认圆角，Tauri 1 默认直角）。
- 排查窗口样式问题用 `DwmGetWindowAttribute(DWMWA_WINDOW_CORNER_PREFERENCE)` + `GetWindowLong(GWL_STYLE)`。

## 2026-10-27：PC 开机自启时好时坏（自启项指向失效建造产物 + --hidden 静默失效）

### 现象
- 开机自启「时好时坏」：有时托盘常驻，有时没有；开机时窗口偶尔弹出来（本应静默）。

### 根因（三层）
1. **自启注册表项是历史遗留且指向失效路径**：`HKCU\...\Run` 里的值名是旧品牌 `QuickPaste`，
   指向 `E:\...\src-tauri\target\release\quickpaste.exe`（开发构建产物）。
   - 该文件后来被 cargo 重新构建删除/覆盖 → 开机启动找不到 exe → 自启失败。
   - 用户日常手动从安装版启动成功，误以为「有时自启成功」→ 主观感觉时好时坏。
2. **`--hidden` 静默启动被覆盖**：`lib.rs` setup 里先 `restore_geometry()`（尾部含 `show()`），
   `--hidden` 分支 `hide()` 之后**又调用了一次 `restore_geometry(app)?`** → 将刚隐藏的窗口再次
   show 出来 → 开机自启不静默（窗口弹出）。
3. **Tauri 1 构建的 exe 依赖同目录 `WebView2Loader.dll`**：本机旧安装版是 Tauri 2 时代构建的
   （无需该 DLL），用 Tauri 1 新构建的 exe 直接覆盖安装目录后启动报
   `0xC0000135 (STATUS_DLL_NOT_FOUND)` 崩溃退出。**Tauri 1 绿色版/手动更新时必须同时带上
   `WebView2Loader.dll`**（正常 NSIS 安装包里 tauri 会自动放入）。

### 修复
1. `cmds.rs qp_set_autostart`：
   - 写入/关闭自启时**先删除旧值名 `QuickPaste`**（历史遗留），避免多个自启项并存。
   - 写入路径**优先取安装目录正式版** `%LOCALAPPDATA%\QuickCopy\QuickCopy.exe`（稳定，不会被
     cargo 构建清理），未安装时才回退 `std::env::current_exe()`。
2. `lib.rs` setup：`--hidden` 分支与 `restore_geometry` 改互斥——
   `if --hidden { set_skip_taskbar + hide } else { restore_geometry }`，删除两次调用。
3. 本机落地：旧 `QuickPaste` 项删除；写入 `"C:\...\QuickCopy.exe" --hidden`；
   安装目录 exe 升级为修复版并补 `WebView2Loader.dll`（从旧 `%LOCALAPPDATA%\QuickPaste\` 复制）。

### 验证
- `QuickCopy.exe --hidden` 启动 → 主窗口不可见 + 进程常驻 + 页面加载 `https://tauri.localhost/` ✅
- 无参启动 → 新实例退出（单实例），常驻实例被唤醒显示主窗口 ✅

### 预防
- 自启项必须指向**安装目录**，不能指向 `target/release` 构建产物。
- Tauri 1 构建/分发 exe 必须带 `WebView2Loader.dll`（检查方式：缺它启动即 0xC0000135）。

## 2026-10-27：PC 拖拽文件失效（Tauri 1/2 拖放事件差异 + CLI 被误升 2.x）

### 现象
- 用户把文件从资源管理器拖到 QuickCopy 窗口放开，应用无反应（查找列表不添加文件）。
- 用户说「之前可以的」。代码 diff 显示拖拽相关代码近期未改。

### 根因（两层叠加）

**根因一：`@tauri-apps/cli` 被误升级到 2.12.3（node_modules 与 lock 不一致）**
- 项目是 **Tauri 1**（`src-tauri/Cargo.toml` → `tauri = "1.7"`/lock 1.8.3；`tauri.conf.json` 是 Tauri 1 schema）。
- 本机 `node_modules/@tauri-apps/cli` 被手动换成 **2.12.3**，但 `package-lock.json` 记录的是 1.6.3。
- Tauri 2 CLI 构建 Tauri 1 项目：config schema 校验报错（`distDir/devPath/withGlobalTauri` unexpected）；即便继续，产物异常——**新构建的 exe 加载 `localhost:1420`（dev server 地址），dev server 一停窗口就 chrome-error 白屏**。用户之前「可以用」是因为当时 dev server 在跑。

**根因二（拖拽失效的直接原因）：Tauri 2→1 降级时 UI 拖放事件没同步改**
- `c3903ec` 提交把项目从 Tauri 2 降级到 Tauri 1，但 `ui/index.html` 的 `bindDrag()` 仍按 Tauri 2 写。
- 两个大版本的事件协议不同（已对照 tauri 1.8.3 源码核实：`manager.rs:71` 事件常量、`manager.rs:1347` 裸数组 payload）：

| | 事件名 | payload |
|---|---|---|
| Tauri 2 | `tauri://drag-drop` | `{ paths: [...], position }` |
| **Tauri 1.8.x（当前）** | **`tauri://file-drop`**（另有 `-hover`/`-cancelled`） | **裸路径数组 `["C:\\...", ...]`** |

- UI 监听 `tauri://drag-drop` + 取 `e.payload.paths` → 事件名不匹配 + payload 结构不匹配，双错。真实拖放时 Tauri 确实 emit 了 `tauri://file-drop`，但 UI 接不住。
- 关键前提已确认成立：wry 0.24.12 的 `file-drop` feature 已启用（`tauri-runtime-wry` 依赖 `wry = { features = ["file-drop","protocol"] }`），OS 拖放事件会产生。

### 修复
1. **CLI 锁回 1.x**：`npm install @tauri-apps/cli@1.6.3 --save-dev`（与 package.json/lock 一致）。
2. **UI 双监听 + 双 payload 兼容**（`ui/index.html` `bindDrag()`）：
   - 同时监听 `tauri://file-drop`（Tauri 1）和 `tauri://drag-drop`（Tauri 2）。
   - payload 分支处理：裸数组 → `handleDroppedPaths(p)`；`{paths}` → `handleDroppedPaths(p.paths)`。
3. 用正确 CLI 重新 `npx tauri build --features custom-protocol`，验证页面加载 `https://tauri.localhost/` + 真实拖放添加文件。

### 验证方式（本机我怎么做检查）
- dev：`npx tauri dev` 前必须确认 `npx tauri --version` 是 **1.x**。
- CDP 检查：`WEBVIEW2_ADDITIONAL_BROWSER_ARGUMENTS=--remote-debugging-port=9222 --remote-allow-origins=*` 启动 exe，`http://127.0.0.1:9222/json/list` 找 `https://tauri.localhost/` 主页面，eval `document.documentElement.innerHTML.indexOf('tauri://file-drop')`。
- 页面加载失败的判据：URL 变成 `chrome-error://chromewebdata/` 或停留在 `localhost:1420`（dev server 依赖）→ 说明构建方式错误。

### 预防
- **AGENTS.md 已加「Tauri 版本管理」强制规则**：CLI 必须 1.x、禁止 Tauri 2 CLI；改 Tauri 大版本时必须检查 `bindDrag()` 事件名/payload。
- 任何「之前可以、现在不行」的 PC 功能问题，先查：当前 exe 是不是异常构建（页面是否白屏/依赖 dev server）。

### 遗留
- **NSIS 安装包目前打不了**：`tauri build` 时需从 `github.com/tauri-apps/binary-releases` 下载 `nsis-3.zip`，本机网络对 github 不可达（代理 127.0.0.1:7890/7891 在跑但 curl/pip 直连失败）；本机也没有 makensis。此前 `bundle/nsis/*.zip` 缓存已失效。**临时用绿色版**：`dist-windows/QuickCopy_0.2.18_x64.exe`（新构建，不依赖 dev server）。网络恢复后可补打包。
  - **已解决（2026-11-11）**：`npx tauri build` 现可用，makensis 已缓存于 `%LOCALAPPDATA%\tauri\NSIS\makensis.exe`；macos 失效不再讨论。自定义安装包走 `installer/build_installer.py`（tauri CLI 构建 + makensis 编译 `installer/QuickCopy.nsi`）→ `dist-release/QuickCopy_<ver>_x64-setup.exe`。

## 2026-11-11：`.output()` 等待子进程在 WebView2 fire-and-forget IPC 下永久挂起（开机自启三态改版踩坑）

### 现象
- 把设置页「开机自启」从 checkbox 改下拉三态后，**用户/脚本从前端调用 `qp_set_autostart` 时注册表从不写入**：
  - CDP 里 `await window.QP.invoke('qp_set_autostart', {mode:'silent'})`（promise 被持有）→ **正常写注册表**；
  - 页面真实 `change` 事件触发 `bootChange()`（fire-and-forget，无 await 持有）→ **注册表不写**，且 **invoke 永不 resolve**（toast 不弹）。
- 后端加了逐步写日志后发现：fire-and-forget 调用时函数执行到 `Command::new("reg").args(...).output()` 前就打住，后面（含写注册表）从未执行；而 direct await 调用同一段代码完整执行（`reg add` exit 0）。

### 根因
- `std::process::Command::output()` 内部是 `spawn() + wait_with_output()`（读子进程 stdout 管道直到 EOF 再 `wait()`）。
- Tauri 1 的同步 command 在 WebView2 IPC 回调线程上执行；当前端以 fire-and-forget 方式调用 invoke（JS 不持有 promise、evaluate 立即结束）时，该 `wait_with_output` 会**永久挂起**，后续代码（注册表写入）永不执行，invoke 也不返回。promise 挂到 `window` 上持有也一样挂——与 JS 引用无关，属 WebView2/Tauri IPC 上下文与子进程等待交互的坑。
- 之前 checkbox 版本用同样的 `T.invoke(...)` 有旧 UI/旧路径，一直没暴露（或从未在真实设备验证过 UI 路径）。

### 修复
- `cmds.rs qp_set_autostart`（Windows 分支）`reg add` / `reg delete` 一律改 **`Command::new("reg").args([...]).spawn()`**，**不 `.output()` 等待**：
  - `reg.exe` 是独立系统进程，`spawn()` 即返回，注册表写入由系统异步完成（毫秒级）；
  - `spawn()` 失败才 `Err`（如 reg.exe 不存在），不再校验退出码。
- 前端 `bootChange()` / 回填统一改走全局 `window.QP.invoke`（与验证口径一致）。

### 验证
- 真实 `change` 事件（等价用户操作）：silent → `reg add ... --hidden` ✅ / front → 无参 `exe` ✅ / off → 删除 ✅；`get_setting('autostart')` 与下拉回填一致 ✅。
- 注意 `autostart_detect_system()`（内部函数、setup 阶段调用，非 IPC 上下文）仍用 `.output()` 读注册表——不受此坑影响。

### 预防
- **Tauri 1 command 里启动子进程一律 `spawn()` 不等待**；需要结果时改用 `std::thread::spawn` + 回调/事件通知，不要在 IPC handler 线程 `wait_with_output`。
- 前端改 IPC 调用后，必须用「真实用户操作路径」验证（CDP 派发 `dispatchEvent(new Event('change'))`，而不是只 `await invoke` 直连），fire-and-forget 与 await 的行为可能不同。
